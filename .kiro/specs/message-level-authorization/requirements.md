# Requirements Document

## Introduction

Message Level Authorization (MLA) extends Apache Kafka's existing topic-level ACL authorization with fine-grained, per-record authorization. A Data Producer specifies which consumers are permitted to receive each individual data event by embedding an authorization bitmap in the record's headers. The Message Bus (Kafka broker) enforces these policies at fetch time through a new broker-side plugin interface, delivering only authorized records to each consumer.

The only change to the Kafka broker is the introduction of a new general-purpose `RecordFetchPlugin` interface that allows plugins to inspect, transform, or filter records during fetch. The MLA logic is implemented as a plugin for this interface.

All other components — the Consumer ID Registry topic, consumer ID management, and bitmap construction — are managed externally by the Data Management Administration and the Data Producer. The Consumer ID Registry is a standard Kafka compacted topic created and maintained by the administrator. The Data Producer reads consumer IDs from this topic and constructs the authorization bitmap in the record header.

## Glossary

- **Message_Bus**: The Apache Kafka broker cluster that stores, replicates, and delivers records. It enforces message-level authorization at fetch time via the Record_Fetch_Plugin.
- **Data_Producer**: A Kafka producer application that generates data events, reads consumer IDs from the Consumer_ID_Registry_Topic, constructs the Authorization_Bitmap, and embeds it in the record header.
- **Data_Consumer**: A Kafka consumer application that subscribes to a topic and receives only the data events it is authorized to consume.
- **Data_Management_Administration**: The administrative role or tooling responsible for creating topics, managing the Consumer_ID_Registry_Topic, and registering/deleting Kafka users with their Consumer_IDs.
- **Record_Fetch_Plugin**: A new general-purpose broker-side plugin interface that the Message_Bus invokes for each record during fetch response construction. The plugin can inspect, transform, or filter records before they are delivered to the consumer. This is the only change to the Kafka broker.
- **MLA_Plugin**: The concrete implementation of the Record_Fetch_Plugin interface that performs bitmap-based message-level authorization by filtering records based on the Authorization_Bitmap.
- **Consumer_ID_Registry_Topic**: A standard Kafka compacted topic created and managed by the Data_Management_Administration. It stores the mapping of Kafka user principals to their auto-incremented Consumer_IDs.
- **Authorization_Header**: A Kafka record header with the key `mla-authz-bitmap` whose value is the serialized Authorization_Bitmap. Each record on an MLA_Enabled_Topic carries this header.
- **Authorization_Bitmap**: A binary bitmap in which each bit position corresponds to a Consumer_ID. A bit set to 1 indicates the consumer is authorized; a bit set to 0 indicates the consumer is not authorized.
- **Consumer_ID**: An auto-incremented integer starting from 0, assigned by the Data_Management_Administration to each Kafka user. The Consumer_ID is global to the cluster and determines the bit position in the Authorization_Bitmap.
- **Consumer_Bitmask**: A per-consumer bitmask generated by the MLA_Plugin, with the bit at the consumer's Consumer_ID position set to 1 and all other bits set to 0.
- **MLA_Enabled_Topic**: A Kafka topic configured with the MLA_Plugin as an active Record_Fetch_Plugin. Records on this topic carry an Authorization_Header.
- **Authorization_Check**: The bitwise operation performed by the MLA_Plugin to determine if a consumer is authorized. The plugin performs a bitwise AND between the Consumer_Bitmask and the Authorization_Bitmap; a non-zero result indicates authorization.

## Requirements

### Requirement 1: Record Fetch Plugin Interface

**User Story:** As a Kafka platform developer, I want a general-purpose broker-side plugin interface for intercepting records during fetch, so that record-level logic such as filtering, transformation, or authorization can be implemented and deployed without modifying core broker code.

#### Acceptance Criteria

1. THE Message_Bus SHALL define a `RecordFetchPlugin` interface with a method that accepts a consumer principal, a topic-partition identifier, and a read-only reference to a record, and returns either a record (original or newly constructed) to include in the fetch response, or null to exclude the record from the fetch response.
2. THE Message_Bus SHALL load Record_Fetch_Plugin instances at broker startup using the existing Kafka plugin configuration mechanism, accepting a comma-separated list of plugin class names.
3. WHEN no Record_Fetch_Plugin is configured, THE Message_Bus SHALL deliver all records without invoking any per-record plugin logic.
4. WHEN multiple Record_Fetch_Plugins are configured, THE Message_Bus SHALL invoke them in the order specified in the configuration for each record during fetch response construction.
5. WHEN a Record_Fetch_Plugin returns null, THE Message_Bus SHALL skip all remaining plugins in the chain and exclude the record from the fetch response.
6. WHEN a Record_Fetch_Plugin returns a record, THE Message_Bus SHALL pass the returned record to the next plugin in the chain.
7. THE Record_Fetch_Plugin interface SHALL provide a method to determine whether the plugin is active for a given topic.
8. THE Message_Bus SHALL pass the authenticated consumer principal to each Record_Fetch_Plugin for each invocation.
9. WHEN the Message_Bus starts each Record_Fetch_Plugin, THE Message_Bus SHALL provide a reference to the configured Authorizer instance, so that the plugin can query ACL bindings and resource-level authorization decisions for extensibility.

### Requirement 2: Topic-Level Record Fetch Plugin Configuration

**User Story:** As a Data_Management_Administration user, I want to specify which Record_Fetch_Plugins are active for a topic at creation time, so that each topic can have its own set of per-record processing plugins.

#### Acceptance Criteria

1. WHEN a topic creation request includes a record fetch plugin configuration, THE Message_Bus SHALL store the list of active plugin class names as part of the topic configuration.
2. WHEN a topic creation request does not include a record fetch plugin configuration, THE Message_Bus SHALL create the topic with no active Record_Fetch_Plugins.
3. IF a topic creation request references a plugin class name that is not loaded at the broker, THEN THE Message_Bus SHALL reject the request and return a descriptive error.
4. THE Record_Fetch_Plugin SHALL use the topic configuration to determine whether it is active for a given topic.

### Requirement 3: Consumer ID Registry Topic Management

**User Story:** As a Data_Management_Administration user, I want to create and manage a Consumer ID Registry topic that maps Kafka users to auto-incremented IDs, so that Data Producers can construct authorization bitmaps.

#### Acceptance Criteria

1. THE Data_Management_Administration SHALL create the Consumer_ID_Registry_Topic as a standard Kafka compacted topic.
2. THE Data_Management_Administration SHALL write a record to the Consumer_ID_Registry_Topic for each Kafka user, with the user principal as the key and the Consumer_ID as the value.
3. THE Data_Management_Administration SHALL assign Consumer_IDs as auto-incremented integers starting from 0.
4. THE Data_Management_Administration SHALL guarantee that no two users share the same Consumer_ID.
5. WHEN a Kafka user is deleted, THE Data_Management_Administration SHALL write a tombstone record (null value) to the Consumer_ID_Registry_Topic for that user's principal.
6. THE Data_Management_Administration SHALL guarantee that retired Consumer_IDs (from deleted users) are never reassigned to new users.
7. THE Data_Management_Administration SHALL document the procedures for backing up, restoring, and mirroring the Consumer_ID_Registry_Topic to other Kafka clusters.

### Requirement 4: Data Producer Consumer ID Resolution

**User Story:** As a Data_Producer, I want to read consumer IDs from the Consumer ID Registry topic, so that I can construct the Authorization_Bitmap for each data event.

#### Acceptance Criteria

1. THE Data_Producer SHALL consume the Consumer_ID_Registry_Topic to obtain the mapping of Kafka user principals to Consumer_IDs.
2. THE Data_Producer SHALL maintain a local cache of Consumer_ID mappings from the Consumer_ID_Registry_Topic.
3. WHEN a new record appears on the Consumer_ID_Registry_Topic, THE Data_Producer SHALL update its local cache with the new or changed Consumer_ID mapping.
4. WHEN a tombstone record appears on the Consumer_ID_Registry_Topic, THE Data_Producer SHALL remove the corresponding user from its local cache.

### Requirement 5: Authorization Bitmap Construction

**User Story:** As a Data_Producer, I want to construct an Authorization_Bitmap encoding which consumers are permitted to receive a specific data event, so that the Message_Bus can enforce per-record authorization.

#### Acceptance Criteria

1. THE Data_Producer SHALL construct an Authorization_Bitmap in which each bit position corresponds to a Consumer_ID, with bit value 1 indicating authorization and bit value 0 indicating no authorization.
2. THE Authorization_Bitmap SHALL use zero-based bit positioning, where the first created Kafka user (Consumer_ID 0) corresponds to bit position 0.
3. WHEN the Data_Producer constructs a bitmap authorizing consumers with Consumer_IDs 2 and 5, THE Data_Producer SHALL produce an Authorization_Bitmap with bits at positions 2 and 5 set to 1 and all other bits set to 0.
4. WHEN the Data_Producer constructs a bitmap authorizing only the first created Kafka user (Consumer_ID 0), THE Data_Producer SHALL produce an Authorization_Bitmap with bit position 0 set to 1 and all other bits set to 0.
5. THE Authorization_Bitmap SHALL use a variable-length byte array to accommodate any number of registered consumers.
6. THE Data_Producer SHALL attach the Authorization_Bitmap as a record header with key `mla-authz-bitmap` on each record produced to an MLA_Enabled_Topic.

### Requirement 6: Consumer Bitmask Generation

**User Story:** As a Message_Bus operator, I want the MLA plugin to generate a per-consumer bitmask for each consumer, so that the plugin can perform efficient bitwise authorization checks.

#### Acceptance Criteria

1. THE MLA_Plugin SHALL read the Consumer_ID_Registry_Topic to obtain Consumer_ID mappings for Kafka users.
2. WHEN a consumer with a Consumer_ID fetches from an MLA_Enabled_Topic, THE MLA_Plugin SHALL generate a Consumer_Bitmask in big-endian bit order with the bit at the consumer's Consumer_ID position set to 1 and all other bits set to 0.
3. THE MLA_Plugin SHALL pad the Consumer_Bitmask to match the byte length of the Authorization_Bitmap being evaluated.
4. THE MLA_Plugin SHALL cache Consumer_Bitmasks for efficient repeated authorization checks.

### Requirement 7: Message-Level Authorization Enforcement at Fetch Time

**User Story:** As a Data_Consumer, I want the Message_Bus to deliver only the data events I am authorized to receive, so that I cannot access data events intended for other consumers.

#### Acceptance Criteria

1. WHEN a Data_Consumer fetches records from an MLA_Enabled_Topic, THE Message_Bus SHALL invoke the Record_Fetch_Plugin chain for each record.
2. WHEN the MLA_Plugin evaluates authorization, THE MLA_Plugin SHALL read the Authorization_Header from the record and perform a bitwise AND between the Consumer_Bitmask and the Authorization_Bitmap; a non-zero result indicates the consumer is authorized.
3. WHEN the authorization check result is non-zero and the MLA_Plugin is configured to strip the Authorization_Header, THE MLA_Plugin SHALL return a new record with the Authorization_Header removed.
4. WHEN the authorization check result is non-zero and the MLA_Plugin is configured to retain the Authorization_Header, THE MLA_Plugin SHALL return the reference to the original record unchanged.
5. WHEN the authorization check result is zero, THE MLA_Plugin SHALL return null.
6. IF a record on an MLA_Enabled_Topic does not contain an Authorization_Header, THEN THE MLA_Plugin SHALL return null.
7. THE MLA_Plugin SHALL provide a configuration property to control whether the Authorization_Header is stripped from authorized records, with stripping enabled by default.

### Requirement 8: Consumer Authentication and Topic-Level Authorization

**User Story:** As a Data_Consumer, I want the Message_Bus to authenticate my identity and authorize my access to the MLA-enabled topic before any message-level authorization checks occur, so that only authenticated and topic-authorized consumers can attempt to consume records.

#### Acceptance Criteria

1. WHEN a Data_Consumer subscribes to an MLA_Enabled_Topic, THE Message_Bus SHALL authenticate the Data_Consumer using the configured authentication mechanism.
2. WHEN a Data_Consumer subscribes to an MLA_Enabled_Topic, THE Message_Bus SHALL verify that the Data_Consumer has topic-level read authorization via the existing ACL mechanism.
3. IF the Data_Consumer fails authentication or topic-level authorization, THEN THE Message_Bus SHALL reject the subscription and return a descriptive error.
4. THE Message_Bus SHALL perform topic-level authorization before invoking the Record_Fetch_Plugin chain for every fetch request.

### Requirement 9: Non-MLA Topic Behavior Preservation

**User Story:** As a Kafka user, I want topics without record fetch plugins to continue functioning without any behavioral changes, so that existing workloads are unaffected.

#### Acceptance Criteria

1. WHEN a Data_Consumer fetches records from a topic that has no active Record_Fetch_Plugins, THE Message_Bus SHALL deliver all records without invoking any per-record plugin logic.
2. THE Message_Bus SHALL impose no additional latency or processing overhead on topics that have no active Record_Fetch_Plugins.

### Requirement 10: Authorization Bitmap Format

**User Story:** As a developer, I want the Authorization_Bitmap to have a well-defined binary format, so that Data Producers and the MLA_Plugin interpret the bitmap consistently.

#### Acceptance Criteria

1. THE Authorization_Bitmap SHALL be a variable-length byte array in big-endian bit order, where bit position 0 corresponds to the most significant bit of the first byte.
2. THE Data_Producer and the MLA_Plugin SHALL use the same bit order convention so that the bitwise AND between the Authorization_Bitmap and the Consumer_Bitmask produces correct results.
3. IF the Authorization_Header contains a zero-length byte array, THEN THE MLA_Plugin SHALL treat the record as unauthorized for all consumers.
4. IF the Authorization_Header byte array is shorter than the Consumer_Bitmask, THEN THE MLA_Plugin SHALL treat the missing bits as 0 (unauthorized).

### Requirement 11: Fetch Response Offset Consistency

**User Story:** As a Data_Consumer, I want offset tracking to work correctly even when records are filtered out by record fetch plugins, so that I do not re-process or skip records after a restart.

#### Acceptance Criteria

1. WHEN the Message_Bus excludes records from a fetch response because a Record_Fetch_Plugin returned null, THE Message_Bus SHALL advance the consumer's fetch position past the excluded records so that subsequent fetches do not re-evaluate them.
2. THE Message_Bus SHALL return the correct high watermark and log start offset in fetch responses regardless of how many records were filtered by Record_Fetch_Plugins.
3. WHEN a Data_Consumer commits offsets, THE Message_Bus SHALL accept the committed offset even if the record at that offset was not delivered to the consumer due to plugin filtering.

### Requirement 12: Record Fetch Plugin Documentation

**User Story:** As a Kafka operator and developer, I want comprehensive documentation of the Record Fetch Plugin interface, so that I can implement custom plugins and understand the impact on fetch behavior.

#### Acceptance Criteria

1. THE Message_Bus documentation SHALL describe the RecordFetchPlugin interface, its lifecycle (initialization, per-record invocation, shutdown), and how to implement a custom plugin.
2. THE Message_Bus documentation SHALL describe the fetch response behavior when Record_Fetch_Plugins filter or transform records, including the impact on consumer offset tracking, fetch byte counts, and consumer lag metrics.
3. THE Message_Bus documentation SHALL describe how to configure Record_Fetch_Plugins at the broker level and at the topic level.

### Requirement 13: MLA Feature Documentation

**User Story:** As a Data_Management_Administration user and Data_Producer developer, I want comprehensive documentation of the MLA feature, so that I can set up and operate message-level authorization.

#### Acceptance Criteria

1. THE MLA documentation SHALL describe the end-to-end MLA workflow: Consumer_ID_Registry_Topic management, Data_Producer bitmap construction, and MLA_Plugin authorization enforcement.
2. THE MLA documentation SHALL describe the Authorization_Bitmap format with examples.
3. THE MLA documentation SHALL describe the procedures for creating, backing up, restoring, and mirroring the Consumer_ID_Registry_Topic.
4. THE MLA documentation SHALL describe the MLA_Plugin configuration properties, including the header stripping option.
